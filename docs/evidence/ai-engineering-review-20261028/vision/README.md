After the first, Windows restarted after a graphics-kernel bugcheck. After the second, the driver reported *"GPU is lost. Reboot the system to recover this GPU"*. GPU work was stopped at that point. Do not cite any number in this folder as a model-quality or capacity result.

The 27 October random-weight technical probe ([`../../ai-engineering-20261027/vision-resnet-open-loop.json`](../../ai-engineering-20261027/vision-resnet-open-loop.json)) is unchanged. As noted below, its CPU row used **one CPU thread per call**.

## Partial observations that are not results

- **Split check (verified twice):**
  - Train, validation and test (4,000 / 1,000 / 1,000 images, seeds 47 / 100,047 / 200,047) share **zero** image hashes, and no split contains a duplicate.
  - Both attempts regenerated byte-identical splits. Aggregate SHA-256 values: train `ad97178e…`, validation `55c6d009…`, test `3c422b81…`; full values are in the attempt reports.
- **Training was far from finished.** In attempt 2, validation accuracy swung between 0.338 and 0.788 over epochs 1-9 while the learning rate was still near its peak, and training accuracy (with flips) rose from 0.53 to 0.80. These numbers say nothing about the final model. The test split was never evaluated.
- **The CPU-only smoke run proved the code path, not a result.** It used a 64 px model trained for one epoch on 16 images, at 10 req/s for 5 s, and is not kept as evidence. It exercised training, weight hashing, test-split regeneration, both ramp runs, accounting and capacity selection. It also showed that the WSL `/proc/stat` aggregate undercounts millisecond bursts (0.1 % busy while the server process alone used 0.44 cores). CPU use is therefore taken from per-process accounting (protocol revision 2).

## Thread settings (all configurations)

The 27 October probe set `torch.set_num_threads(1)` and `torch.set_num_interop_threads(1)` (`scripts/measure_vision_engineering.py`, `run_load_probe`), recorded as `cpu_threads_per_call: 1`. Its CPU row (177 of 1,000 served) is therefore a one-thread result, not a fair CPU baseline.

| `cpu_fp32_dynamic` | CPU FP32 | 1 | 8, 2 ms | PyTorch default = **8** (all physical cores) | default = 8 | Fair CPU baseline |
| `cpu_fp32_dynamic_1thread` | CPU FP32 | 1 | 8, 2 ms | 1 | 1 | Historical comparison only |

| `gpu_fp32_dynamic_cache50` | GPU FP32 | 1 | 8, 2 ms | 4 | 1 | Cache lever, 50 % byte-identical repeats of 32 hot images |

The host has 8 physical cores and 16 logical CPUs (Intel Core i9-9900K under WSL2). On it, PyTorch's default is 8 intra-op and 8 inter-op threads. Every ramp report records:

- `torch.get_num_threads()` and `torch.get_num_interop_threads()`;
- the defaults before any setting was applied;
- the physical and logical core counts.

Training uses 4 intra-op threads for host-side data handling.

## Method (as specified, not yet executed)

- **Task:** classify a procedural 224 x 224 RGB bottle image as `good`, `missing_cap`, `scratch` or `misaligned_label`. The defect rules are fictional and listed in the protocol. No real image or personal data is used.
- **Input size:** 224 x 224 keeps per-image compute and the 150,528-byte body identical to the 27 October probe. The thinnest scratches (0.9-1.8 px at 224 px) would fall below one pixel at 112 px.
- **Model:** the same ResNet-18 shape as the probe with a 4-class head, trained from random initialization; no download. Training settings:
  - AdamW with a one-cycle schedule peaking at 1e-3;
  - 15 epochs, batch 64, horizontal flips;
  - the epoch is selected on validation only, then the test split is evaluated once in FP32 and FP16.
- **Service:**
  - one Python process: `ThreadingHTTPServer` plus `BoundedBatchVisionService` (64 waiting requests, HTTP 429 when full);
  - a fresh server and queue for each step.
- **Clients:**
  - separate spawned asyncio processes sending raw HTTP/1.0, one connection per request;
  - absolute send times that never wait for earlier responses;
  - at most 256 open requests per process (excess recorded as `not_sent`).
- **SLO (fixed before runs):**
  - p99 end-to-end ≤ 100 ms, measured from the *scheduled* arrival, over every HTTP 200 answer, late answers included;
  - failure share ≤ 1 % of all offered requests. Failures are 429, errors, timeouts, `not_sent`, and answers after 1,000 ms;
  - points with an achieved send rate below 95 % of the target are `generator_limited` and excluded from capacity;
  - p99 is flagged unreliable below 1,000 observations.
- **Ladder:**
  - 10, 25, 50, 100, 200, 400, 800, 1,600 and 3,200 req/s, each with 5 s of warm-up and 20 s measured;
  - stop after a step with more than 20 % failures or a generator-limited step;
  - rerun the highest passing and the first failing rate to three runs each;
  - capacity is the highest rate at which every run passed, below the first rate with any failing run.

## 100,000 req/s: formula only, no measured input yet

```text
replicas      = ceil(100,000 / (capacity_at_SLO × (1 − headroom)))
N+1           = replicas + 1
zone variant  = ceil(replicas / (zones − 1)) × zones     # survives the loss of one zone
```

The protocol assumes headroom = 0.3 and three zones. `capacity_at_SLO` must come from a completed ramp; none exists, so no replica count is given here. Shared components cap any such scenario independently of replica count:

- **Load balancer and network.** Raw 150,528-byte bodies at 100,000 req/s are 15.05 GB/s, or about 120 Gbit/s. This is arithmetic, not a measurement.
- **Image decoding.** It is absent from this lab because bodies are raw RGB.
- **Storage and logging.**
- **The control plane.**

`replicas_for_target` implements the formula and is unit-tested on fixed numbers. It is a sizing scenario, never a validated measurement.

## Before any rerun

1. **Reboot.** Windows requires it to recover the GPU. This is the owner's decision; no reboot was attempted here.
2. **Check the card's health under load before training.** Log temperature, power draw, SM clock and throttle reasons at 1 Hz, for example `nvidia-smi --query-gpu=timestamp,temperature.gpu,power.draw,clocks.sm,clocks_throttle_reasons.active --format=csv -l 1`. Run a short load first. Investigate the cause (cooling, power delivery, driver) before a 15-epoch run.
3. **Run alone under one lock.** Use the sequence below and keep the whole GPU sequence (training, evaluation, all ramp configurations, CUDA unit test) inside one lock, with the 60-minute budget and the drop order recorded in the protocol.

## Reproduction commands

Run them from the repository root in WSL. Set `VISION_PYTHON=/root/.local/share/multimodal-ft-venv/bin/python` (torch 2.8.0+cu126, Python 3.12.3) and choose an empty evidence directory outside the checkout, for example `EVIDENCE_DIR=/root/vision-review-YYYYMMDD`.

```bash
# Tests. CPU only; the CUDA consistency case also runs when a GPU is visible.
CUDA_VISIBLE_DEVICES= "$VISION_PYTHON" -B -m unittest tests.test_engineering_vision -v

# 1. Generate splits, check hashes, train 15 epochs, evaluate the test split once.
#    Writes packaging_resnet18_224.pt with a .json sidecar (file SHA-256, test-split hash, input size).
"$VISION_PYTHON" -B scripts/measure_vision_engineering.py --train-packaging --output "$EVIDENCE_DIR/training" \
  --require-cuda --epochs 15 --training-batch 64 --cpu-threads 4 --train-gpu-memory-mib 4096

# 2. One ramp per configuration, each into a new directory, in this order:
#    gpu_fp32_dynamic gpu_fp32_batch1 gpu_fp16_dynamic gpu_fp32_dynamic_2workers
#    gpu_fp32_dynamic_cache50 cpu_fp32_dynamic [cpu_fp32_dynamic_1thread]
for cfg in gpu_fp32_dynamic gpu_fp32_batch1 gpu_fp16_dynamic gpu_fp32_dynamic_2workers gpu_fp32_dynamic_cache50 cpu_fp32_dynamic cpu_fp32_dynamic_1thread; do
  "$VISION_PYTHON" -B scripts/measure_vision_engineering.py --ramp --ramp-config "$cfg" \
    --trained-weights "$EVIDENCE_DIR/training/packaging_resnet18_224.pt" --output "$EVIDENCE_DIR/ramp/$cfg" \
    --duration 20 --ramp-warmup-seconds 5 --key-point-repeats 3 --gpu-memory-mib 512 --queue-size 64
done
```

- **Expected durations:**
  - data generation: about 36 s for 6,000 images, measured twice;
  - training: 5.5-12.6 s per epoch observed on the lone GPU before the failure;
  - each ramp step: about 30 s;
  - each GPU configuration: 4-7 minutes, estimated;
  - whole sequence: about 50 minutes, estimated.
- **Resources:**
  - training allocator cap 4,096 MiB, ramp cap 512 MiB;
  - about 900 MB of host RAM for the splits;
  - a 150 MB payload file per ramp directory.
- **What the scripts do not do:** they take no GPU lock themselves. Serialize GPU access externally.
- **Docs check:** `python scripts/check_engineering_documentation.py` passes, with every new function, method, nested helper and test documented.

## Limits that will apply even after a successful rerun

- Procedural images with fictional defect rules: accuracy describes this generator only.
- One WSL host: server and client processes share the CPU with each other and with the Windows desktop, and the GPU also drives the desktop. nvidia-smi values are device-wide.
- Loopback, raw RGB bodies: no TLS, authentication, real network or image decoding.
- Capacity resolution is limited to the ladder rates.
- Two workers share one GPU and one Python process. This is not multi-node replication.
- GPU training is not bit-reproducible; the weights-file hash identifies the evaluated weights.
